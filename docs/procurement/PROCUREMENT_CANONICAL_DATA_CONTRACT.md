# Procurement Canonical Data Contract

Status: Proposed
Date: 2026-05-15
Scope: Documentation / governance / architecture only

本輪為 canonical contracts phase only。

本文件不涉及 production code、不涉及 DB migration、不涉及 secrets / env、不涉及 Readdy UI 修改、不產生 API route、不實作 Edge Function。後續需由 CTO review 後才可進入 implementation phase。

## 1. Purpose

This document defines the canonical data entities for the 大皇居 B2B procurement platform.

The goal is to give Procurement, LINE Bot, Sales, AI Agent, Sake Admin, Meat Admin, and future Readdy/Codex implementation work the same vocabulary before any schema or runtime code is created.

This is not a database schema. Field names below are conceptual contract names only.

## 2. Entity Ownership Summary

| Entity | Purpose | Owner | Cross-domain usage |
| --- | --- | --- | --- |
| `customers` | Customer company or buying organization | Platform Core | Procurement, Sales, LINE Bot, AI Agent, Sake, Meat |

| `sales_reps` | Internal sales owner profile | Platform Core / Sales Ops | Customer ownership, quote review, follow-up |

| `product_categories` | Category taxonomy | Platform Catalog | Navigation, pricing rules, segmentation |

## 3. UUID Conventions

Recommended conventions:

1. Every canonical entity uses an immutable UUID primary identifier.
2. UUIDs should be generated by the system, not by AI or external clients.
3. Human-readable numbers may exist separately, for example `quote_number`, `order_number`, or `customer_code`.
4. External IDs from LINE, suppliers, ERP, POS, or Readdy should be stored as scoped external references, not reused as canonical IDs.
5. Idempotency keys should be used for event ingestion and draft creation, especially LINE messages and AI-generated quote drafts.
6. Future multi-tenant implementation should include `tenant_id` or equivalent scope on all tenant-owned transactional entities.

Suggested conceptual identifier pattern:

| Concept | Example semantic |
| --- | --- |
| Canonical UUID | `id` |
| Tenant scope | `tenant_id` or `platform_org_id` |
| External reference | `external_refs[]` or scoped reference table |
| Human-readable code | `customer_code`, `quote_number`, `order_number` |
| Idempotency | `source_event_id`, `idempotency_key` |

## 4. Canonical Entity Contracts

### 4.1 `customers`

Purpose: Represents a customer company, restaurant group, distributor, corporate buyer, or other buying organization.

Ownership: Platform Core owns identity and lifecycle. Sales and Procurement may enrich commercial context but should not create duplicate identities.

Canonical relationships:

- has many `customer_locations`
- has many `customer_users`
- has many `quote_requests`, `quotes`, `order_drafts`, `orders`
- may have many `customer_price_rules`
- may have many `procurement_lists`
- may be assigned to one or more `sales_reps` by scope

Cross-domain usage:

- Sake Admin may reference a customer for sake orders or merchant CRM.
- Meat Admin may reference a customer for meat procurement or future B2B orders.
- LINE Bot uses customer identity to resolve conversation context.
- AI Agent may summarize customer-safe context only.

Archive strategy: Soft delete with `archived_at`, `archived_by`, `archive_reason`. Do not hard delete if quotes, orders, messages, or audit records exist.

Multi-tenant consideration: A future platform may allow one legal customer to buy across several product lines. Keep customer identity platform-scoped while enforcing per-tenant visibility.

### 4.2 `customer_locations`

Purpose: Represents a physical or billing location under a customer, such as a restaurant branch, kitchen, warehouse, billing office, or delivery destination.

Ownership: Platform Core owns canonical address/location identity. Sales and customers may request updates.

Canonical relationships:

- belongs to `customers`
- may be referenced by `quote_requests`, `quotes`, `order_drafts`, `orders`
- may have delivery preferences and receiving constraints

Cross-domain usage:

- Procurement uses it for delivery and quote context.
- Shipment uses it for fulfillment planning.
- Sales uses it for territory and account hierarchy.

Archive strategy: Soft archive closed branches. Historical orders retain the original location snapshot or immutable reference.

Multi-tenant consideration: Location visibility should follow customer account permissions and product-line entitlement.

### 4.3 `customer_users`

Purpose: Represents a human buyer, approver, requester, chef, manager, or finance contact linked to a customer.

Ownership: Platform Core owns identity linkage. Customer admins and Sales may manage invitations subject to approval.

Canonical relationships:

- belongs to `customers`
- may be scoped to one or more `customer_locations`
- may link to LINE identity through customer context governance
- may approve `quotes` or confirm `order_drafts`

Cross-domain usage:

- `/b2b` authentication and authorization.
- LINE Bot identity resolution.
- Audit trail for customer confirmation.

Archive strategy: Deactivate rather than delete. Retain confirmation and audit history.

Multi-tenant consideration: One human may belong to multiple customer accounts only through explicit membership records.

### 4.4 `sales_reps`

Purpose: Represents internal sales ownership for customers, quote review, follow-up, and relationship context.

Ownership: Platform Core / Sales Ops.

Canonical relationships:

- may own `customers`, `customer_locations`, or product-line-specific account scopes
- reviews `quote_drafts`
- confirms high-risk `quotes` or `orders`
- receives `followup_recommendation` events

Cross-domain usage:

- Procurement uses sales owner for review and approval.
- LINE Bot routes customer inquiries to the responsible sales rep.
- AI Agent may draft recommendations for the assigned sales rep.

Archive strategy: Deactivate rep profile when role changes. Historical ownership assignments must remain traceable.

Multi-tenant consideration: Sales ownership may vary by tenant, product line, region, or customer location.

### 4.5 `products`

Purpose: Represents a product family or sellable product concept across categories, before SKU/spec granularity.

Ownership: Platform Catalog, with Sake/Meat/Procurement category stewards.

Canonical relationships:

- belongs to one or more `product_categories`
- has many `product_variants`
- may reference Sake or Meat domain-specific product details through governed mappings

Cross-domain usage:

- Procurement catalog and B2B search.
- Sake Admin product references for wine/liquor-specific operations.
- Meat Admin product references for meat-specific operations.
- AI product search.

Archive strategy: Archive discontinued products while preserving quote/order history.

Multi-tenant consideration: Product visibility and sellability may be tenant/product-line scoped.

### 4.6 `product_variants`

Purpose: Represents SKU-level sellable items such as size, vintage, pack, cut, grade, unit, or tableware specification.

Ownership: Platform Catalog.

Canonical relationships:

- belongs to `products`
- may appear in `supplier_quotes`, `price_books`, `customer_price_rules`, `quote_drafts`, `quotes`, `order_items`, `procurement_list_items`
- may map to inventory item references in Sake or Meat domains

Cross-domain usage:

- Procurement quoting and ordering.
- Inventory allocation.
- Supplier sourcing.

Archive strategy: Archive unavailable variants. Do not reuse variant IDs for new specs.

Multi-tenant consideration: Variant availability may differ by tenant, supplier, warehouse, product line, or customer segment.

### 4.7 `product_categories`

Purpose: Canonical taxonomy for alcohol, machine-related products, aged meat, tableware, sourcing-only goods, and future categories.

Ownership: Platform Catalog.

Canonical relationships:

- parent/child category tree
- linked to `products`
- used by `price_books` and `customer_price_rules`

Cross-domain usage:

- B2B navigation.
- Pricing rules.
- AI product classification.
- Tableware initial governance as procurement category.

Archive strategy: Archive unused categories only after remapping products. Do not delete historical category references.

Multi-tenant consideration: Category visibility can be tenant/customer scoped.

### 4.8 `supplier_sources`

Purpose: Represents supplier, importer, wholesaler, producer, or sourcing channel for products or variants.

Ownership: Procurement.

Canonical relationships:

- has many `supplier_quotes`
- may supply many `product_variants`
- may be linked to product-line steward approvals

Cross-domain usage:

- Supplier procurement required events.
- Cost volatility handling.
- Sourcing lead time.

Archive strategy: Archive inactive suppliers. Retain quote history and cost references.

Multi-tenant consideration: Supplier visibility, negotiated terms, and cost access are internal-only and tenant restricted.

### 4.9 `supplier_quotes`

Purpose: Supplier-side quote for cost, availability, MOQ, lead time, expiration, and sourcing conditions.

Ownership: Procurement.

Canonical relationships:

- belongs to `supplier_sources`
- references `product_variants`
- may support `quote_drafts` and `quotes`

Cross-domain usage:

- Margin review.
- Imported liquor volatility.
- Aged meat supply/pricing volatility.
- AI summary, not automatic pricing.

Archive strategy: Expire by `valid_until`; archive manually if invalidated. Never overwrite historical supplier quotes used for customer quotes.

Multi-tenant consideration: Cost and supplier quote data is high-sensitivity internal data and must never be exposed to customer users.

### 4.10 `price_books`

Purpose: Governed pricing layer such as market reference, list price, campaign price, channel price, or category price.

Ownership: Procurement / Finance.

Canonical relationships:

- applies to `product_variants`, `product_categories`, customer segments, or date ranges
- feeds `customer_price_rules` and quote calculations

Cross-domain usage:

- Customer-facing price computation.
- Margin guardrails.
- AI pricing assistant constraints.

Archive strategy: Version price books. Do not overwrite prices after customer quotes or orders reference them.

Multi-tenant consideration: A tenant may have separate price books by product line, region, or customer segment.

### 4.11 `customer_price_rules`

Purpose: Customer-specific pricing rule, discount, fixed price, category price, temporary campaign, or negotiated exception.

Ownership: Procurement / Sales Ops, with Finance guardrails.

Canonical relationships:

- belongs to `customers`
- may scope to `customer_locations`, `product_categories`, `products`, or `product_variants`
- feeds `quote_drafts` and `quotes`

Cross-domain usage:

- B2B price display.
- Sales quote review.
- AI risk alerts.

Archive strategy: Use effective dates and archive expired or superseded rules. Never hard delete rules used in historical quotes.

Multi-tenant consideration: Customer price rules must be scoped to customer and tenant; no cross-customer inference.

### 4.12 `quote_requests`

Purpose: Intake record for customer inquiry before quote drafting.

Ownership: Procurement / Sales.

Canonical relationships:

- belongs to `customers`
- may reference `customer_users`, LINE identity, `customer_locations`, product text, requested items
- may produce one or more `quote_drafts`

Cross-domain usage:

- LINE inquiry.
- `/b2b` request.
- Sales-created inquiry.
- AI product search input.

Archive strategy: Close, cancel, or archive stale requests. Retain source context for audit.

Multi-tenant consideration: All requests must be scoped to customer and product-line entitlement.

### 4.13 `quote_drafts`

Purpose: Internal editable quote draft before customer-facing quote is issued.

Ownership: Procurement / Sales.

Canonical relationships:

- derived from `quote_requests` or `order_drafts`
- references products, supplier quotes, price rules, sales rep, and approval state
- may become `quotes`

Cross-domain usage:

- AI can create draft suggestions.
- Sales reviews pricing, margin, supply, delivery, and customer fit.
- Procurement verifies supplier conditions.

Archive strategy: Version or archive abandoned drafts. Never overwrite final quote history.

Multi-tenant consideration: Drafts may contain sensitive pricing and margin data; access is internal role scoped.

### 4.14 `quotes`

Purpose: Customer-facing quote with version, expiration, line items, terms, and confirmation state.

Ownership: Procurement / Sales.

Canonical relationships:

- belongs to `customers`
- derived from `quote_drafts`
- may convert to `order_drafts` or `orders`
- references accepted version and customer confirmation

Cross-domain usage:

- Customer confirmation in `/b2b` or LINE.
- Sales approval.
- Future order conversion.

Archive strategy: Quotes expire by `valid_until`. Archive cancelled or superseded versions, preserving audit.

Multi-tenant consideration: Customer users only see their own quotes and never supplier cost or internal margin.

### 4.15 `order_drafts`

Purpose: Pre-confirmation order candidate created from LINE, `/b2b`, quote acceptance, procurement list, or sales action.

Ownership: Procurement / Sales.

Canonical relationships:

- belongs to `customers`
- may reference `quotes`
- contains draft line items and delivery preferences
- may become `orders` after approvals

Cross-domain usage:

- LINE cart flow.
- `/b2b` checkout.
- Sales final review.
- AI may suggest but not confirm.

Archive strategy: Expire abandoned drafts. Retain conversion linkage if it becomes an order.

Multi-tenant consideration: Drafts remain customer scoped and should not allocate inventory until approved policy allows.

### 4.16 `orders`

Purpose: Confirmed commercial order after customer and required sales approvals.

Ownership: Commerce / Procurement, with downstream fulfillment ownership by inventory/shipment domains.

Canonical relationships:

- belongs to `customers`
- has many `order_items`
- may derive from `quotes` or `order_drafts`
- may produce supplier procurement, inventory allocation, and shipment readiness events

Cross-domain usage:

- Inventory allocation.
- Supplier procurement.
- Shipment readiness.
- Finance and reporting.

Archive strategy: Orders are not soft-deleted in normal flow. Use cancellation, void, or correction workflows.

Multi-tenant consideration: Orders must be tenant/customer scoped and immutable enough for audit.

### 4.17 `order_items`

Purpose: Confirmed order line item, including product variant, quantity, unit, agreed price, and fulfillment status.

Ownership: Commerce / Procurement.

Canonical relationships:

- belongs to `orders`
- references `product_variants`
- may reference supplier sourcing or inventory allocation

Cross-domain usage:

- Fulfillment.
- Margin reporting.
- Supplier procurement.
- AI follow-up recommendations.

Archive strategy: Do not delete confirmed order items. Use cancellation/adjustment records.

Multi-tenant consideration: Customer users may see agreed price and item details, but never internal cost/margin.

### 4.18 `procurement_lists`

Purpose: Reusable customer purchasing list for common orders, reorders, or recurring needs.

Ownership: Procurement / Customer Success.

Canonical relationships:

- belongs to `customers`
- may scope to a `customer_location`
- has many `procurement_list_items`
- may produce `quote_requests` or `order_drafts`

Cross-domain usage:

- `/b2b` quick reorder.
- Sales planning.
- AI recommendation and preference memory.

Archive strategy: Archive obsolete lists. Keep historical list usage references.

Multi-tenant consideration: Lists are customer-owned context and should not be used to infer another customer's demand.

### 4.19 `procurement_list_items`

Purpose: Item inside a reusable procurement list, including preferred variant, quantity, unit, substitution tolerance, and notes.

Ownership: Procurement / Customer Success.

Canonical relationships:

- belongs to `procurement_lists`
- references `product_variants` or sourcing placeholders
- may seed `quote_requests` and `order_drafts`

Cross-domain usage:

- Demand signal.
- AI reorder suggestions.
- Sales follow-up.

Archive strategy: Archive or deactivate unavailable list items rather than deleting them.

Multi-tenant consideration: Preference memory is customer scoped and must not leak across customers.

## 5. Canonical Relationship Map

```text
customers
-> customer_locations
-> customer_users
-> sales ownership
-> quote_requests
   -> quote_drafts
      -> quotes
         -> order_drafts
            -> orders
               -> order_items

products
-> product_variants
-> product_categories
-> supplier_quotes
-> price_books
-> customer_price_rules

customers
-> procurement_lists
   -> procurement_list_items
      -> quote_requests / order_drafts
```

## 6. Soft Delete And Archive Policy

Default policy:

1. Master data entities use soft archive, not hard delete.
2. Transactional entities use state transitions, cancellation, void, or correction workflows.
3. Any entity used in quote, order, audit, or event history must retain a stable reference.
4. Archive fields should include who, when, why, and replacement reference if any.
5. AI-generated drafts may be archived, but the source event and review trace should remain.

## 7. Future Multi-Tenant Considerations

Future implementation must answer these before migration:

1. Is `customers` platform-global or tenant-local with deduplication?
2. Can one customer buy across Sake, Meat, and Procurement under one account?
3. Are price books tenant-specific, product-line-specific, or platform-wide?
4. How are supplier costs isolated across business units?
5. Which entities require row-level tenant scope?
6. How are historical quotes preserved when customer ownership changes?

Until these are reviewed, this document remains a canonical contract, not an implementation authorization.
